## Configure local capabilities

When the user asks to configure Remotion, WorkBuddy performs the work itself:

1. Check the current machine and the intended OpenMontage use path. Distinguish
   "present somewhere" from "usable for this request".
   Read the verified Package's actual Remotion requirements and supported project
   selection/configuration route. Compare existing projects against the required
   entry, composition and inputs, dependency versions, and browser runtime. If the
   Package supports an external project, inspect that configured project too;
   missing dependencies in the Package's own composer folder alone do not prove
   Remotion unusable. Preserve existing installations and user projects.
   Inspect the browser locations supported by that route; not finding one named
   headless-browser folder does not prove every supported browser is absent.
2. Distinguish compatible and already connected, compatible but not connected,
   proved missing/incompatible parts, and unverified requirements. If the existing
   project is suitable, reuse it: propose only any necessary supported connection
   change, not a new sample project or reinstall merely because a newer version
   exists. An unperformed render test alone is not an installation failure.
3. Explain the smallest necessary next action and final check. For changes, give
   a short plan covering scope, permission, download source if needed, and likely
   disk impact. Obtain consent before downloading, installing, changing settings
   or an existing project, or producing a test output. Inspection-only requests
   remain read-only. An unverified installation identity is not permission to
   install Remotion.
4. Use the current stable Remotion version that is compatible with the verified
   OpenMontage Package. Do not hard-code a version in this Skill.
5. In mainland China, search `https://npmmirror.com` when useful and install npm
   packages through `https://registry.npmmirror.com`. A search result proves only
   that a package is listed, not that installation or OpenMontage use succeeds.
6. Remotion dependencies belong to the compatible project used by the verified
   Package; a global CLI installation alone is not the target. Preserve a usable
   existing location. If new installation is needed, use the product-supported
   writable runtime location outside the immutable Package root, with Windows
   resolving the standard location for the approved scope. Explain permission or
   scope changes and obtain consent. Never assume a drive letter, require a custom
   folder, or install dependencies directly into an immutable Package copy.
7. Install the complete compatible dependency set, including the browser runtime
   required by the chosen Remotion route. Do not report a partial installation as
   ready.
8. After approved configuration, or when reusing an already connected project,
   verify that the current Package's intended use path discovers that same project.
   With test-output consent, make one real minimal Remotion invocation through
   that Package and validate the output. A standalone demo, detection-only call,
   version print, or forcing a readiness flag is not final proof. Without that
   invocation, report the render test as unverified, not passed or failed.
9. Report the exact result. If the user declines, installation fails, or final use
   is not proved, leave the FFmpeg path available and wait for the user's choice
   before retrying, changing scope, or changing source.
